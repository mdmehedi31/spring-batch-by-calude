Spring Batch Mastery Guide

For a Java 21 developer who already knows Spring Boot, JPA, MySQL and REST. First principles to production, targeting Spring Batch 6 on Spring Boot 4, with notes for version 5.

Versions and how to read this guide

Spring Batch 6.0.x on Boot 4.0.x (Java 17+). Many systems still run 5.2 on Boot 3.5, so differences are flagged.

Each topic follows: concept, why, when, internals, example, common mistakes, production practice. Code uses 6.x packages. The capstone code was written carefully but not compiled in the environment that produced the guide, so compile it on day one.

1. Fundamentals

Bulk, non-interactive, restartable processing.

Spring Batch gives you a Job/Step/read-process-write model, chunked transactions, a metadata store for monitoring and restart, ready-made readers and writers, skip/retry, and scaling options. It does not schedule jobs and has no UI.

Online / real-timeBatch
One request is one unit of workOne run is millions of units
Latency mattersThroughput matters
Failure: user retriesFailure: restart without duplicating work
One transaction per requestOne transaction per chunk

It maps to ETL: ItemReader extracts, ItemProcessor transforms, ItemWriter loads.

Use it for

Nightly settlement, file imports, migrations, reports, reconciliation, archiving.

Skip it for

Tiny scripts, a single INSERT ... SELECT, streaming workloads.

Practice: decide up front who triggers jobs and how operators restart them. Run each job in its own JVM or container.

2. Architecture

Who does what.

Trigger (cron, REST, CLI)
   -> JobOperator -> Job -> Step -> Step
                              |-- Reader / Processor / Writer
   JobRepository  ->  MySQL BATCH_* tables
Job / Step

A named flow of steps. A step is a tasklet or a chunk loop, and is the unit of restart and transaction.

Reader / Processor / Writer

Reader returns one item per call, null at end. Processor handles one item. Writer gets the whole chunk.

JobRepository

Persists every run. Called at start, at each chunk commit, and at step end.

JobOperator

Start, restart, stop, abandon. Replaces JobLauncher in v6.

ExecutionContext

Persisted key/value map. Step scope is saved each commit (reader position). Job scope passes small data between steps.

Calling a Job bean like a method creates no metadata. Always go through JobOperator.

3. Job

The concept people get wrong: instance versus execution.

Job "importJob"
 |- JobInstance #1 = name + identifying params {runDate=2026-10-01}
 |     |- JobExecution #1 (FAILED)
 |     '- JobExecution #2 (COMPLETED)   restart of the same instance
 '- JobInstance #2 = {runDate=2026-10-02}
  • One instance can have many executions.
  • A COMPLETED instance cannot run again (JobInstanceAlreadyCompleteException), which prevents double-processing.
  • Only one execution of an instance runs at a time.
  • Non-identifying parameters do not create a new instance.
@Bean Job importJob(JobRepository repo, Step importStep, Step reportStep) {
  return new JobBuilder("importJob", repo)
      .start(importStep).next(reportStep).build();
}
StatusMeaningRestartable
STARTEDRunningn/a
COMPLETEDDoneNo
FAILEDUnrecoverable errorYes
STOPPEDStopped on request after current chunkYes
ABANDONEDOperator says never restartNo
Zombie STARTED. If the JVM is killed, the row stays STARTED and restart fails with JobExecutionAlreadyRunningException. Confirm the process is dead, then recover or mark it. v6 adds graceful shutdown on SIGTERM to reduce this.
Mistake: a timestamp as an identifying parameter makes every launch a new instance, so restart never happens. Use stable keys such as file name or business date.

4. Step

Tasklet or chunk.

Tasklet

One action, called repeatedly until it returns FINISHED, each call in its own transaction. File moves, one SQL statement, notifications.

Chunk-oriented

Read N, process each, write all, commit. About 90% of real batch.

new ChunkOrientedStepBuilder<TxCsv, Tx>("importStep", repo, 500)
    .reader(reader).processor(processor).writer(writer)
    .transactionManager(tx).build();

Useful StepExecution counters: read, filter, write, commit, rollback and skip counts. Sanity check: read - filter - processSkip = write.

Mistake: looping over records inside a tasklet loses chunking, skip, retry and mid-step restart. Keep steps small and single-purpose.

5. Readers

Only read() returning null ends the step.

A reader that never returns null loops forever. One that returns null too early ends the step successfully with data silently missing. Readers that implement ItemStream save their position in update(), committed with each chunk, and restore it in open().

ReaderThread-safeNotes
FlatFileItemReaderNoStreams a file; needs unique .name(); restart assumes file unchanged
JdbcCursorItemReaderNoOne cursor for the whole step. MySQL buffers all rows unless useCursorFetch=true plus fetchSize
JdbcPagingItemReaderYesKey-based paging; unique sort key; best default for big tables
JpaPagingItemReaderYesOFFSET paging, slow on deep pages; needs ORDER BY
RepositoryItemReaderYesSpring Data pageable method, offset paging
Offset paging while updating the filtered column (for example status='NEW' to 'DONE') skips rows. Key-based paging is safe.
Practice: align page size with chunk size, project to DTOs, index sort and filter columns, and rehearse a kill-and-restart.

6. Processor

Per-item business logic. Same null, opposite meaning from the reader.

OutcomeHowCounted as
Keep / transformreturn an objectwrite count
Filter (normal rule)return nullfilterCount
Reject (bad data)throw, with skip configuredprocessSkipCount
Abortthrow an unskippable exceptionstep FAILED

Processors run inside the chunk transaction and are re-run on retry or rollback, so keep them pure and repeatable. Avoid per-item remote or SQL lookups (preload a map or join in the reader SQL), and avoid side effects.

Practice: log every reject with its key, and unit-test processors with plain JUnit.

7. Writers

One batched operation per chunk is where speed is won.

WriterUse whenWatch out
JdbcBatchItemWriterVolumeAdd rewriteBatchedStatements=true on MySQL; use upserts. Records need an explicit parameter-source lambda
JpaItemWriterNeed JPA lifecycleSlower; IDENTITY ids disable insert batching
RepositoryItemWriterSmall volumePer-item save() is convenient, not fast
FlatFileItemWriterFile outputTruncates to last commit on rollback; name files by run date
INSERT INTO transactions (tx_id, amount, fee) VALUES (:txId, :amount, :fee)
ON DUPLICATE KEY UPDATE amount = VALUES(amount), fee = VALUES(fee)
HTTP calls and message sends are not rolled back with the database. If the call succeeds and the commit fails, the chunk repeats, so the remote side needs idempotency keys.

8. Chunk processing

One chunk, one transaction.

begin tx -> read x N -> process each -> write(chunk)
         -> update step ExecutionContext + metadata -> commit

Business data and metadata commit atomically, so a restart never repeats committed work and never loses an uncommitted position. At most one chunk is redone.

Chunk sizeEffect
10100,000 commits per million rows; metadata dominates. Fine for debugging or heavy per-item work
100Reasonable default, good for JPA
1000Often fastest for JDBC batch; longer locks, bigger rollback

Start at 500 to 1000 for JDBC and 100 to 200 for JPA, then measure. Make chunk size a configuration property.

9. Transactions

The step owns them.

  • A chunk is one transaction. In a tasklet each execute call is one.
  • Step execution and context updates join the chunk transaction. Job-level updates use short transactions of their own.
  • Keep business tables and metadata in the same database so one transaction manager covers both.
  • REQUIRES_NEW commits even when the chunk rolls back: right for reject logs, wrong for business data.

When a chunk fails without skip or retry, everything before the last commit stays and the in-flight chunk is lost. With skip on a writer failure, the framework scans the chunk item by item to find the bad one, which is expensive.

@Bean PlatformTransactionManager tm(DataSource ds){ return new JdbcTransactionManager(ds); }

10. Parameters and scopes

Parameters exist only at launch, so late-bound beans need a scope.

@Bean @StepScope
FlatFileItemReader<TxCsv> reader(@Value("#{jobParameters['inputFile']}") String f) { ... }
  1. At startup Spring registers a scoped proxy.
  2. When the step starts, the real bean is built with the parameters resolved.
  3. It is cached for that step execution and destroyed at the end.
@StepScope

One instance per step execution. Can read job params, job context, step context.

@JobScope

One instance per job execution. Job params and job context only.

Return the concrete type (FlatFileItemReader), not ItemReader, or the proxy hides ItemStream and no restart position is saved. Validate parameters with DefaultJobParametersValidator.

11. Metadata tables

The metadata is the product.

TableHolds
BATCH_JOB_INSTANCEName and JOB_KEY (hash of identifying params), unique together
BATCH_JOB_EXECUTIONOne attempt: status, exit code, times
BATCH_JOB_EXECUTION_PARAMSParameters per execution
BATCH_STEP_EXECUTIONCounters per step
BATCH_STEP_EXECUTION_CONTEXTThe checkpoint, e.g. {"txReader.read.count":4500}
BATCH_JOB_EXECUTION_CONTEXTShared job state

Every chunk commit updates the step execution and its context, so large contexts and ever-growing tables slow everything.

SELECT je.JOB_EXECUTION_ID, ji.JOB_NAME, je.STATUS, je.LAST_UPDATED
FROM BATCH_JOB_EXECUTION je JOIN BATCH_JOB_INSTANCE ji USING (JOB_INSTANCE_ID)
WHERE je.STATUS IN ('STARTED','STARTING','STOPPING');
Practice: create the schema with migrations, add a retention job, keep the context tiny, never edit rows by hand. Failed v5 instances cannot be restarted under v6.

12. Restartability

Resume, do not start over.

  1. Create a new execution for the same instance.
  2. Skip steps that COMPLETED (unless allowStartIfComplete).
  3. Copy the failed step's last context.
  4. reader.open(ctx) jumps to the saved position and the loop continues.
Position-based

Line count or last id in the context. The default.

Marker-based

Rows go NEW to DONE in the same transaction.

Idempotent rerun

Upserts, rerun the step. Simplest for short jobs.

What breaks it: input changed between failure and restart, non-idempotent writes, stateful readers in multi-threaded steps, timestamp parameters, a different job definition.

Practice: keep a CI test that injects a failure at item N, restarts, and asserts the data equals an uninterrupted run.

13. Error handling

Classify the exception, then pick the tool.

ToolFor
Fail (default)Unexpected errors
SkipPermanently bad data
RetryTransient: deadlock, timeout, network
RestartFix the cause and relaunch
new ChunkOrientedStepBuilder<TxCsv, Tx>("importStep", repo, 500)
  .reader(r).processor(p).writer(w).transactionManager(tx)
  .faultTolerant()
  .skip(FlatFileParseException.class).skip(InvalidTxException.class).skipLimit(100)
  .retry(TransientDataAccessException.class).retryLimit(3)
  .skipListener(rejectListener)
  .build();
  • Always pair skip with skipLimit and retry with retryLimit.
  • Reader skip is cheap. Processor skip re-processes the chunk. Writer skip scans item by item, so validate in the processor.
  • Retry re-runs processors, so they must be repeatable and writers idempotent.
  • Record rejects with a SkipListener and mark the exit status COMPLETED WITH SKIPS.
Never skip(Exception.class) with a huge limit. You will "succeed" with data missing. Treat the skip limit as a safety valve: a 40% reject rate means the file is bad.

14. Performance tuning

Find the bottleneck first.

SymptomFirst fix
DB busy on insertsJDBC batch, rewriteBatchedStatements, bigger chunk
App CPU highProfile the processor, precompute lookups
Slow as data growsKey-based paging, indexes, purge metadata
OutOfMemoryErrorEnable cursor streaming, smaller chunk, tiny context
Lock waitsSmaller chunks, partition by key range, retry on deadlock
VolumeRecommendation
~10kKeep it simple. Chunk 100 to 500, JPA is fine
~100kJDBC batch writer, chunk 500 to 1000, page size equals chunk size
~500kJDBC reader and writer, chunk 1000, preload lookups, maybe 4 to 8 threads
1M+Partition by key range, chunk 1000 to 2000, idempotent upserts, set-based SQL where possible, dedicated JVM

Benchmark at real volume, not 1,000 rows. These are starting points, not guarantees.

15. Scaling

Pick the simplest option that meets your window.

OptionHow it worksTrade-off
Multi-threaded stepChunks run on a thread poolReader must be thread-safe; position restart lost (saveState(false))
Parallel stepsIndependent flows via splitOnly helps with independent steps
Local partitioningKey ranges, one worker step each, same JVMMore code, restart works per partition
Remote partitioningWorkers on other nodes read their own data via a shared repositoryNeeds broker and shared DB
Remote chunkingManager reads, workers process and writeItems cross the network; single reader
For 1M+ rows on one machine, use local partitioning. Across machines, running N independent jobs with a shard parameter (for example as Kubernetes Jobs) is often simpler than a messaging topology.

Mistakes: non-thread-safe readers in threaded steps, overlapping or gapped partitions, connection pool smaller than the thread count.

16. Interview preparation

Open each answer after trying it yourself.

JobInstance versus JobExecution?

An instance is the logical run (name plus identifying parameters). An execution is one attempt. One instance can have several executions, and a completed instance cannot run again.

Reader null versus processor null?

Reader null means end of input. Processor null means filter this item: not written, filterCount increments, nothing fails.

What happens when a job fails halfway and you restart it?

A new execution is created for the same instance. Completed steps are skipped. The failed step opens with the context from its last commit, so the reader skips ahead. At most one chunk is redone, so writes must be idempotent.

Why does @StepScope exist?

Job parameters are unknown at startup. A proxy is registered, and the real bean is built when the step starts with #{jobParameters[...]} resolved. Return the specific type so ItemStream stays visible.

Why is a writer skip more expensive than a reader skip?

A failed batch write does not identify the bad item, so the chunk is re-processed and re-written one item at a time. A reader skip just moves to the next line.

Exactly-once effects across a database and an external API?

Not cheaply. Make both sides idempotent: upsert for the database, an idempotency key for the API. Or write an outbox row in the chunk transaction and deliver it separately.

A job completes but wrote zero rows. Why?

Check the BATCH_STEP_EXECUTION counts. Likely causes: the reader query matches nothing, parameters bound empty, the processor filters everything, or the writer SQL matched no rows with assert updates off.

What changed in Spring Batch 6?

JobOperator replaces JobLauncher, JobRepository subsumes JobExplorer, new ChunkOrientedStep with Framework 7 retry, immutable domain model, package moves, schema sequence rename, a resourceless default in Boot 4, and Jackson 3.

17. Production best practices

Logging

Put the execution id in the MDC. Log at job and step boundaries, log rejects with keys, never log per item at INFO or log sensitive fields.

Monitoring

v6 needs an ObservationRegistry bean. Short-lived jobs die before Prometheus scrapes, so push or use the metadata tables.

Alerts

Failed, running too long, stale LAST_UPDATED, skip counts, and a missing run.

Deployment

One job per container, Kubernetes CronJob as scheduler, spring.batch.job.enabled=false, secrets never in parameters.

Anti-patternFix
Record loop in a taskletChunk step
chunk(1)500 to 1000 for JDBC
Per-item lookup in processorPreload map or join
Per-item save for millionsJDBC batch writer
Never purging metadataRetention job
Non-idempotent writesUpserts or idempotency keys
Only testing the happy pathRestart, skip, retry and volume tests
Production checklist
  • Idempotent writes; restart tested
  • Stable identifying parameters and a validator
  • Skip limits, reject recording, retry only for transient errors
  • Chunk, page and pool sizes as measured config properties
  • MySQL: rewriteBatchedStatements, cursor streaming, indexes checked with EXPLAIN
  • Schema migrated; retention job in place
  • Metrics, logs with execution id, alerts including missing run
  • Graceful shutdown and a zombie-execution runbook
  • MySQL Testcontainers integration tests

    .transactionManager(tx)
    .faultTolerant()

    .skipListener(skipListener)
    .build();

The processor

public Tx process(TxCsv in) {
  if (in.amount() == null) throw new InvalidTxException("amount missing", in.txId()); // skip
  if (!CURRENCIES.contains(in.currency())) throw new InvalidTxException("bad currency", in.txId());
  if (in.amount().signum() == 0) return null;                                          // filter
  BigDecimal fee = in.amount().abs().multiply(FEE_RATE).setScale(2, RoundingMode.HALF_UP);
  return new Tx(in.txId(), in.accountId(), in.amount(), in.currency(), in.txDate(), fee);
}
